# Compromises & conventions

What is **simplified or stubbed for the hackathon**, why it is acceptable for the submission,
and what a production build would have to solve. This consolidates notes that also live in
`docs/PROBLEM.md` (scope), `docs/EVALUATION.md` (limitations), and `docs/DECISIONS.md`
(D-0014 / D-0015 / D-0016). Nothing here is a defect in what was built — it is the boundary
of what was built.

The submission's own acceptance bar (D-0016): **a judge with no hardware and no API key can
walk the whole integrator path and reproduce the main result.** Every convention below is
chosen to keep that true.

| **5 frozen frames from one capture session.** "Held-out" here is **spatial, not temporal** — no re-shoot at a different time of day, no lighting drift, no fresh cycle-state variety. n = 22 determinate observations; one committed sample per config (plus 2 author-attested re-runs that are not reproducible). | The comparison is fair (same frames, same metric for baseline and every iteration) and every number reproduces byte-for-byte from `--replay`. ## Config & architecture

| Convention (hackathon) | Why it is acceptable for the submission | Production TODO | Ref |
| --- | --- | --- | --- |
| **The offline eval reads only committed inputs; the git-ignored runtime layers are invisible to it.** It uses the static `config` singleton (`laundry3.config.ts` + defaults), `data/machines.json`, `data/corrections/`, and the **committed** `data/site-config.json` (per-camera `machineIds` scoping for every mode; `mask` / `maskLegend` for `--mode=roi`). It never reads the git-ignored `data/config-overrides.json` (portal `PATCH /api/config`) or `data/reservations.json`, and `src/agent/pipeline.ts` shape-sniffs `data/site-config.json` so the portal's camera-list shape cannot feed the `--mode=agent` calibration path. | A clean checkout reproduces every number from `--replay`; the git-ignored portal layers cannot perturb it. Editing a camera's machine-id list in the portal *does* rewrite the committed `data/site-config.json` and would re-scope a later eval — but that file is version-controlled, so any such change shows in `git status`. | One config path — the eval reads the same site config the runtime serves, with an explicit "as committed at SHA X" pin for reproductions. | `docs/DECISIONS.md` D-0015 amendments; `docs/EVALUATION.md` |
| **No Docker image, no `docker compose`, no runtime polling loop, no `snapshot.json` publisher.** The judge runs `npm run dev`; `buildRoomStatus` reads a committed eval report, not a live snapshot. | D-0016 P0 (correction loop clickable key-free on the frozen dataset) is the "must ship" bar and it is met. The container is P1. | Ship the D-0016 P1 container: Next.js app + `ffmpeg` + the loop, a writable `/data` volume, `snapshot.json` as the portal's source. | D-0016 P1 |
| **Machine reference-state screenshots are not wired.** `POST /api/upload` accepts `kind=machine-reference`, but there is no editor UI and the eval does not consume them. | Few-shot reference images are an optional calibration input in D-0015; the submission's results do not depend on them. | The reference-image UI + inject the crops as few-shot image blocks in the classify call. | D-0015 (Partial) |
| **Two experiments are kept as documented negative results, not features.** `--mode=calibrated` (annotated shot + mask as extra vision inputs, −13.7 pp on the 5-frame set) still replays from the committed `data/cache/calibrated/`. The verification pass (−4.4 pp, measured on the **retired 9-frame set**) is config-gated off (`agent.verification.enabled=false`), its cache was removed in the 2026-08-29 recut, and its evidence is the historical report under `docs/artifacts/historical/`. | The changelog rule asks for removed experiments and what they taught. | Nothing — negative results, retained for the record. | `docs/CHANGELOG.md`; `docs/trajectories/runtime/2026-08-29-verification-pass-retired.md` |

## Portal actions (ground rules 4 / 5)

| Convention (hackathon) | Why it is acceptable for the submission | Production TODO | Ref |
| --- | --- | --- | --- |
| **Reservations are simulated in-repo.** `data/reservations.json` (git-ignored), no login, an anonymous per-browser id, a best-effort per-user cap. Pre-emption reconciliation (a walk-in taking a held machine) is **not wired**. There is **no outbound notification channel** — a real push / SMS would be a new consequential action needing its own sandbox + approval (ground rule 4). | The only outward action is a soft, auto-expiring, in-portal hold — reversible, low impact, simulated. This is exactly what ground rule 4 asks for. | Real identity; a durable hold store; pre-emption reconciled on every state refresh; opt-in notifications with an explicit approval step. | `docs/PROBLEM.md` "Consequential actions"; D-0007 |
| **The write routes have no authentication.** `POST /api/corrections`, `/api/machines`, `/api/cameras`, `/api/upload`, `/api/refresh`, `PATCH /api/config`, `POST /api/reservations` — all write into the repo (or its git-ignored runtime files) with no gate: a local / on-prem trust boundary where the operator is trusted. Ids are regex-restricted so a body cannot path-traverse. | The integrator runs this as a local service on their own machine (D-0016); the submission is walked on `localhost`. | An integrator auth gate before this is exposed on any shared or public host. | route docstrings; D-0016 |
| **No per-frame human review at runtime.** The solution is calibration-reviewed only. A wrong "free" is low-harm by design — it reproduces today's wasted trip and nothing worse; no hardware or money moves. The portal shows a per-machine confidence and a "confirm on arrival" caveat. | Ground rule 5 is met at calibration (a human confirms/corrects every machine before the per-site config is accepted). The runtime harm assessment is written out in `docs/PROBLEM.md` and is revisitable. | A flag-low-confidence review queue with a qualified reviewer. | `docs/PROBLEM.md` "Human reviewer" |
